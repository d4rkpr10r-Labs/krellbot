# M32: venue capability truth, accounts and request budgets

**Status:** proposed; agents start M32 only after the owner merges it and
after earlier milestone files' agent tasks, unless the owner reorders.

**Depends on:** M28 (P01: M28.3, M28.22–M28.27, F04 live order truth; P02:
M28.5, F12 feed failure codes, and M28.1, F17 per-occurrence alert dedupe).
M30 (M30.1 paper ledger, for the accounts view). M31 (M31.7 moves the
scheduled-fetch venue set into `data/scheduled_venues.py`, which M32.2
reads).

**Exit / gate:** one backend-served, test-pinned record per venue says what
is qualified, which public data, research, key and preflight paths exist,
how a protective stop actually works, which order policy is used and which
fee is assumed. The frontend reads it instead of hand-written venue copies.
Rate-limit stops reach Operations and notify once. The workstation shows
plainly that each venue has one account. Nothing promotes a venue to native
stops or to live.

Rules for every task are in `AGENTS.md`. Agents skip `[owner]` tasks.
`PAPER_ONLY_RELEASE` stays True. Tests use fake transports and fake
keyrings. `GET /api/v1/capabilities` stays pinned; the matrix gets its own
route. No edits to `live_preflight.py`, `secrets.py`, `keys/` or order shapes
in `venues/` unless a task says so. UI follows `docs/design-system.md`
(`KRELL-SIGNAL-20261010`).

**Decisions adopted from the approved roadmap:**

- Decision 7: P07 stays declarations-only until the owner reconciles M27.5
  (third live venue) with PARKING line 16 and product direction in M32.1.
  The only non-declaration venue task, M32.6, waits for that decision.
- Decision 13: rate-limit alerts use the existing opt-in desktop and email
  channels. Telegram, if ever, comes later as an opt-in channel disclosed in
  `docs/telemetry.md`, not here.
- Keys stay in the OS keychain (PARKING line 12). Multiple accounts per venue
  need the owner's M32.9 decision before any design work.

**Parallelism:** M32.2 ∥ M32.3 ∥ M32.7 first. M32.4 after M32.3. M32.5 after
M32.2. M32.6 after M32.1 and M32.3. M32.8 after M32.2.

## Epic M32-A — Venue capability truth

- [ ] **M32.2 One backend venue capability matrix.** New read-only
  `application/venue_capabilities.py` composes `secrets.VENUES`,
  `distribution_venues`, the scheduled-fetch venue set, `KEYS_VENUES`,
  research venues, `SUPPORTED_PREFLIGHT_VENUES`,
  `WEB_LIVE_ARM_PREFLIGHT_VENUE` and the domain stop capability (read, never
  edited); region reads 'global endpoint only'. A new session-gated route
  serves it, and `marketAvailability.ts` and `qualifiedLiveVenues.ts` read it
  instead of hard-coded tables, which fixes MEXC shown as replay-only.
  - Scope: `src/krellbot/application/venue_capabilities.py` (new), `src/krellbot/data/scheduled_venues.py` (from M31.7, read only), `src/krellbot/cli.py`, `src/krellbot/api/app.py`, `frontend/src/features/paper/marketAvailability.ts`, `frontend/src/markets/qualifiedLiveVenues.ts`

  - Accept: `KRELLBOT_HOME=$(mktemp -d) uv run --no-sync pytest -q tests/test_venue_capability_matrix.py && (cd frontend && npm run test:unit -- --run src/features/paper/marketAvailability.fromMatrix.test.ts)`

## Explicitly out of M32

- Promoting any venue to native stops or to live, and editing the qualified
  registry (M27.5 after M32.1).
- Order-shape changes in `venues/`, real limit, post-only, TIF, chase or
  timeout policies (they need their own milestone and M28.26, the former
  PARKING line 20 fix, first).
- Fee-token balance alerts and automatic top-up (F50 waits for a venue with
  fee-token support).
- Shared request budgets and per-venue throttles across all adapters (need
  multiple accounts first).
- Kraken private-call throttle units: M28.33.
- Telegram or any new notifier channel.
